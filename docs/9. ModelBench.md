# ModelBench — Sutra

## 1. What this is

Measured capability bake-off of the six models available on the **api.b.ai** OpenAI-compatible endpoint, run to pick Sutra's composer model. Every model answered the **same 5 tasks + latency measurement**; the composite is a **score out of 100**.

- **Run date:** 2026-09-01 (sequential run with pacing; earlier parallel attempt invalidated by provider rate limit — see §6)
- **Harness:** `.apitest/run_bench.py` (Python 3.11, urllib, temp=0, max_tokens=400 primary pass + 2000-token fairness re-run)
- **Raw outputs:** `.apitest/raw/*.txt` (per model × per task), machine-readable `.apitest/results.json`
- **Reproduce:** `python .apitest/run_bench.py` (~6–7 min; pacing built in)

**Scope note:** this is a *capability* bench (instruction following, math, strict JSON, runnable code, Hindi WhatsApp copy, latency). It is *not* the composer-level judge scoring — that lives in [`sutra/scripts/model_bench.py`](../sutra/scripts/model_bench.py) and produces /50 judge-rubric scores. Capability scores here tell us *which* models are worth spending judge samples on.

## 3. Methodology

### 3.1 Task battery and weights

| Task | Weight | Prompt (condensed) | Pass condition |
|---|---|---|---|
| `exact` | 15 | "Reply with exactly this text and nothing else: MAGICPIN_RULES_2026" | Byte-exact match (contains = 10/15) |
| `math` | 20 | Rs 500 item → 20% discount → +10% tax on discounted price; reply with only the number | `440` present (500×0.8×1.1) |
| `json` | 25 | Return ONLY a valid JSON object with keys `name, offer_text, discount_percent, city` for a Chai Point Bangalore offer; no markdown | Parsed as dict + all 4 keys (valid dict w/ missing keys = 15/25) |
| `code` | 15 | `def second_largest(nums)` without sorting; reply with only code | **Actually executed**: 3 asserts pass (`[4,1,7,3]→4`, `[10,3,5]→5`, `[2,9,2,8]→8`); `.sort()/sorted()` use caps at 10/15 |
| `hindi` | 10 | Max-30-word WhatsApp offer message: Chai Point Bangalore, 50% off masala chai; message only | Contains offer % + brand, ≤45 words |
| `speed` | 15 | Mean wall-clock of the 5 calls | <2s=15, <4s=12, <7s=9, <12s=6, else 3 |

Settings: `temperature=0`, `max_tokens=400` primary pass; **2000-token fairness re-run** for the `code` task (and `hy3` hindi) after diagnosing reasoning-token burn (§5.2). Code was verified by writing the model's output to a temp `.py`, appending asserts, and executing it with a 15s timeout — no eyeballing.

### 3.2 Why temp=0 and why execution-verified code

Sutra's composer runs at temp=0 with a hard 25s timeout (TechSpec AI-4, Rules D-01/L-01). The bench mirrors that. Code scores come from real execution, not "looks right" — the same standard Sutra's validation gate applies to LLM output.

## 4. Per-task detail

### 4.1 Exact instruction following — all 6 models: 15/15

Every model returned `MAGICPIN_RULES_2026` byte-exact at temp=0. Good signal for format-sensitive composer work.

### 4.2 Math — all 6 models: 20/20

All models chained discount-then-tax correctly (440). No model fell into the "add 10% of original" trap.

### 4.3 Strict JSON reliability — all 6 models: 25/25

All six emitted parseable JSON with all four keys (after fence-stripping) at temp=0. No model wrapped JSON in prose.

5 models produced on-spec ≤30-word messages with offer % and brand. `hy3` returned empty content at 400 tokens (reasoning burn), 10/10 at 2000 tokens.

## 5. Operational findings (matters more than the scores)

### 5.1 Hard rate limit: ~9–10 requests/minute per key

Measured: a burst of 8 parallel calls all returned 200; calls 10+ in the same rolling window returned `429`. First bench attempt (6 models in parallel) had every model's *first* task pass and *all subsequent* tasks 429 — the tell that it's a per-minute rolling window, not a concurrency cap.

**Client rule for any script/bot using this endpoint:** sequential dispatch, ≥6.5s pacing between calls, and 429 backoff (10s → 25s → 45s). The bench harness implements exactly this.

### 5.2 All six are reasoning models — `max_tokens` must cover thinking

Responses carry a separate `reasoning_content` field + `completion_tokens_details.reasoning_tokens`. If `max_tokens` is too small, the entire budget is consumed by reasoning and `content` comes back **empty** with `finish_reason: "length"`.

Measured worst case: `deepseek-v4-flash-vision-exp` burned **all 3000 tokens on reasoning** (12,811 chars of thinking, zero content) on the code task — a genuine infinite think-loop, not a budget issue. `hy3` and `glm-5.3-flash` behave the same on that task.

**Client rule:** `max_tokens ≥ 1500–2000` for structured/code tasks; treat empty-`content` + `finish_reason=length` as a model-failure signal → fallback tier (matches Sutra's existing three-tier fallback, ADR-07).

### 5.3 Transient 429s ("model busy")

`glm-5.3-flash` intermittently returned `429 {"error":{"message":"The model service is currently busy…"}}` independent of the per-minute window. One retry cleared it. Any client needs at least one retry on 429.

### 5.4 Prior provider attempts (context for why this endpoint)

| Provider / key | Result |
|---|---|
| OpenRouter `poolside/laguna-s-2.1:free`, `poolside/laguna-xs-2.1:free` | Valid key, but free-tier daily cap (50/day) already exhausted → 429 until midnight UTC |
| First supplied key (`sk-nJyl…`, non-`sk-or-v1-` format) | 401 `Missing Authentication header` on every auth-checked endpoint — not a valid OpenRouter key |
| **api.b.ai (this bench)** | ✅ All 6 models reachable, OpenAI-compatible, no daily cap observed (only per-minute rate limit) |

## 6. Recommendation for Sutra

| Use | Model | Why |
|---|---|---|
| **Primary composer** | `deepseek-v4-flash` | 97/100, 2.91s avg, perfect JSON + runnable code, 3× faster than qwen |
| **Secondary / fallback** | `qwen3.8-flash` | 94/100; passed code within 400 tokens (most token-efficient); different failure profile from primary |
| Avoid for structured output | `vision-exp`, `hy3`, `glm-5.3-flash` | Think-loops → empty content → gate rejects → wasted latency |
| Tertiary at best | `mimo-v2.5` | Capable (91) but 10.15s avg latency is risky against the 25s budget under parallel load |

**Suggested config:**

```
CUSTOM_LLM_BASE_URL=https://api.b.ai/v1
CUSTOM_LLM_API_KEY=<b.ai key — see SESSION-SUMMARY / .env>
CUSTOM_LLM_MODEL=deepseek-v4-flash
CUSTOM_LLM_MAX_TOKENS=2000
```

## 7. Honesty / limitations of this bench

- 1 sample per task per model (temp=0 keeps it deterministic-ish, but provider-side routing can vary) — 5-sample re-runs would tighten variance.
- Capability tasks ≠ composer quality; a model can be a great coder and a mediocre WhatsApp copywriter. The `hindi` task is a proxy, not the real rubric.
- The `code` task re-run used a larger token budget for models that burned reasoning at 400 — scored at their best achievable config, which is fairer but optimistic vs a fixed-budget production setting.
- api.b.ai is an aggregator-style endpoint; model→provider routing may change under us without notice. The three-tier fallback (ADR-07) is the structural defense.
