# TechSpec — Sutra

## 1. System Overview

Sutra is a single-process stateful HTTP service exposing six endpoints to the magicpin judge harness. It receives incremental context pushes, decides on each tick whether to initiate conversations, composes context-grounded WhatsApp messages via a hybrid LLM+guardrail pipeline, and replies to simulated merchant/customer messages via a heuristic classifier + state machine. All state lives in-memory with a 30-second disk snapshot for restart recovery.

**Architecture one-liner:** *Hybrid deterministic-guardrail composer: routed LLM core + facts-registry validation gate + three-tier fallback + reply state machine.*

## 3. Technology Stack

| Layer | Choice | Rationale |
|---|---|---|
| Language | Python 3.11+ | Async support; FastAPI native; LLM SDK maturity |
| Web framework | FastAPI | Async; Pydantic v2 validation; auto OpenAPI |
| Validation | Pydantic v2 | Strict schemas; rejects malformed outbound |
| HTTP client | httpx (async) | Non-blocking LLM calls; provider fallback |
| LLM SDKs | anthropic, openai (or equivalent) | Primary + secondary on different providers |
| Hosting | Render / Fly / Railway (persistent process) | NOT serverless — cold starts + state loss violate 60-min persistence |
| Process mgmt | uvicorn (single worker) | Avoids race on in-memory stores |
| Monitoring | UptimeRobot (external) + structured logs | 3-strike healthz prevention |
| Snapshot | Atomic temp-file + rename | Crash-safe persistence |
| Test harness | `judge_simulator.py` (official) + custom synthetic tests | Local gate before submission |

## 5. Backend Architecture — Endpoint Contracts

### 5.1 `GET /v1/healthz`

**200 OK:**
```json
{
  "status": "ok",
  "uptime_seconds": 3600,
  "contexts_loaded": {
    "category": 5,
    "merchant": 50,
    "customer": 200,
    "trigger": 100
  }
}
```
- Counts derived from `context_store` at request time: `len([k for k in store if k.scope == "category"])`, etc.
- Polled every 60s by harness; 3 consecutive non-200 = disqualification (−10).
- Latency budget: 2s.

### 5.2 `GET /v1/metadata`

**200 OK:**
```json
{
  "team_name": "[TEAM_NAME]",
  "team_members": ["[MEMBER_1]", "[MEMBER_2]"],
  "model": "claude-sonnet-4-5 + gpt-4o-mini fallback",
  "approach": "Hybrid deterministic-guardrail composer: routed LLM core + facts-registry validation gate + three-tier fallback + reply state machine",
  "contact_email": "team@example.com",
  "version": "1.0.0",
  "submitted_at": "2026-04-29T08:00:00Z"
}
```

### 5.3 `POST /v1/context`

**Request:**
```json
{
  "scope": "merchant",
  "context_id": "m_001_drmeera",
  "version": 3,
  "payload": { ... },
  "delivered_at": "2026-04-29T10:00:00Z"
}
```

**Decision tree:**
- If `Content-Length > 500 KB` → 400 `{"accepted": false, "reason": "payload_too_large", "max_bytes": 500000}`
- If `scope` invalid → 400 `{"accepted": false, "reason": "invalid_scope", "details": "..."}`
- If `version == stored.version` → 200 no-op `{"accepted": true, "ack_id": "...", "stored_at": "..."}`
- If `version < stored.version` → 409 `{"accepted": false, "reason": "stale_version", "current_version": <stored>}`
- If `version > stored.version` (or new key) → atomic replace → 200 `{"accepted": true, "ack_id": "...", "stored_at": "..."}`
- Mark `fresh_context_registry[(scope, context_id)] = {latest_version: version, pending: True}`
- Latency budget: 5s; must not block on LLM work.

### 5.4 `POST /v1/tick`

**Request:**
```json
{
  "now": "2026-04-29T10:30:00Z",
  "available_triggers": ["trg_research_digest_dentists"]
}
```

**Response (≤20 actions):**
```json
{
  "actions": [
    {
      "conversation_id": "conv_drmeera_research_w17_01",
      "merchant_id": "m_001_drmeera",
      "customer_id": null,
      "send_as": "vera",
      "trigger_id": "trg_research_digest_dentists",
      "template_name": "vera_research_digest_v1",
      "template_params": ["Dr. Meera", "JIDA Oct issue"],
      "body": "...",
      "cta": "open_ended",
      "suppression_key": "research:dentists:2026-W17",
      "rationale": "..."
    }
  ]
}
```

- Empty actions valid: `{"actions": []}`.
- One action per `(merchant_id, conversation_id)` per tick.
- Required fields: `conversation_id`, `merchant_id`, `customer_id` (nullable, not omitted), `send_as`, `trigger_id`, `template_name`, `template_params`, `body`, `cta`, `suppression_key`, `rationale`.
- Latency budget: 10s soft, 30s hard.

### 5.5 `POST /v1/reply`

**Request:**
```json
{
  "conversation_id": "conv_001",
  "merchant_id": "m_001_drmeera",
  "customer_id": null,
  "from_role": "merchant",
  "message": "Yes, send me the abstract",
  "received_at": "2026-04-29T10:45:00Z",
  "turn_number": 2
}
```

**Action `send`:**
```json
{
  "action": "send",
  "body": "...",
  "cta": "open_ended",
  "rationale": "..."
}
```

**Action `wait`:**
```json
{
  "action": "wait",
  "wait_seconds": 1800,
  "rationale": "..."
}
```

**Action `end`:**
```json
{
  "action": "end",
  "rationale": "..."
}
```

- `wait_seconds` ∈ {900, 1800, 3600} — never 86400 in 60-min window.
- After `end`, no further messages on that `conversation_id`.
- Latency budget: 10s soft, 30s hard.

### 5.6 `POST /v1/teardown` (optional)

**200 OK:**
```json
{
  "teardown": true,
  "wiped_at": "2026-04-29T11:30:00Z",
  "stores_cleared": ["context_store", "conversation_store", "suppression_registry", "body_hash_registry", "topic_registry", "fresh_context_registry", "response_cache", "llm_ledger"]
}
```
- Wipes everything; preserves only anonymized aggregate metrics (total calls, total cost) for billing audit.

### AI-2: Facts Registry & Validation Gate (13 checks, enforced order)

```
┌──────────────────────────────────────────────────────────────────┐
│  FACTS REGISTRY EXTRACTION (pre-LLM, from CURRENT context ver)   │
│  ─ numbers (views, calls, CTRs, prices, peer_stats)             │
│  ─ dates (last_visit, expires_at, festival date)                │
│  ─ citations (professional_journals, regulatory_authorities)    │
│  ─ names (owner_first_name, merchant name, customer name)       │
│  ─ offer prices (from offer_catalog)                            │
│  ─ localities (city, locality)                                  │
│  ─ computed numbers (customer_aggregate cohort counts)          │
└──────────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│  LLM CALL (temp=0, top_p=1, 25s hard timeout)                  │
│  primary → secondary (diff provider) → fallback template       │
└──────────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│  VALIDATION GATE (13 checks, enforced order)                    │
│  1. URL scan (regex) — reject if any URL in body                │
│  2. Facts membership — every number/date/citation/name traces  │
│  3. Single CTA — no multiple-CTA patterns                      │
│  4. CTA in last sentence                                       │
│  5. CTA policy matches trigger.kind (binary vs slot vs open)   │
│  6. Taboo word scan (per-vertical taboo list)                  │
│  7. Domain vocab presence (≥1 vertical-specific word)           │
│  8. Language match (output matches identity.languages[0])       │
│  9. Owner first name greeting (when available)                 │
│ 10. ≥4–5 verifiable facts woven around one spine signal        │
│ 11. Body-hash anti-repetition (no verbatim repeat in conv)      │
│ 12. Similarity vs case studies (<0.6 Jaccard)                  │
│ 13. Rationale facts ⊆ body facts                              │
│                                                                  │
│  On any fail: re-prompt ONCE with stricter instruction         │
│  On second fail: deterministic fallback template                │
│  All rejections logged with reason code                         │
└──────────────────────────────────────────────────────────────────┘
```

### AI-3: Reply Classifier (pattern table)

| Class | Trigger patterns (case-insensitive substring/regex) | Bot action |
|---|---|---|
| `auto_reply` | verbatim match 3+ turns in same conv OR signatures: "thank you for contacting", "automated assistant", "team tak pahuncha", "bahut-bahut shukriya", "main ek automated assistant hoon", "aapki jaankari ke liye bahut-bahut shukriya" | flag-once → wait 1800s → end |
| `explicit_intent` | "let's do it", "go ahead", "yes", "ok", "haan", "kar do", "kardo", "bhejo", "send karo", "mujhe karna hai", "sign me up", "i want to join", "chaloo karo" | action mode immediately (verbs: done/sending/drafting/confirm) — ZERO further qualifying questions |
| `hostile` | "stop messaging", "leave me alone", "chodo", "don't bother", "spam", abuse/slur patterns | polite end: "Koi baat nahi. Best wishes!" |
| `off_topic` | out-of-scope asks: "file GST", "tax help", "legal advice", "investment", "loan" | decline + redirect: "Yeh mission ke bahar hai, but main aapke GBP/account par focus kar sakti hoon. Want me to continue with X?" |
| `question` | contains "?" OR interrogative words: "what", "how", "why", "kya", "kaise", "kyun", "kahan" | answer + re-pitch CTA |
| `objection` | "no", "not interested", "maybe later", "busy", "nahi", "baad mein", "abhi nahi" | acknowledge + counter-offer OR end |
| `accept` | anything not matching above | action mode |

**Classifier implementation:** regex-first (deterministic, fast); LLM classifier as tiebreaker only if multiple classes match (rare). Avoids LLM call latency for the common case.

### AI-4: Model Strategy

| Tier | Model | Role | Temperature | Cache | Token budget |
|---|---|---|---|---|---|
| Primary | Frontier (Anthropic Claude Sonnet 4.5 or equivalent) | Composition + rationale | 0, top_p=1 | yes (hash-keyed) | ~2K input, ~500 output |
| Secondary | Fast (OpenAI GPT-4o-mini or equivalent) | Composition fallback when primary times out / errors | 0, top_p=1 | yes (separate cache namespace) | ~2K input, ~500 output |
| Tertiary | Deterministic fallback templates | Always available; never times out | N/A | N/A | 0 LLM tokens |

**Composition prompt structure:**
- System prompt: voice profile (per-vertical), language, CTA policy, judgment hook, taboo list, required-vocab list, "no URLs" rule, "single CTA in last sentence" rule
- User prompt: 4 contexts (truncated to relevant fields), chosen spine signal + 2-3 supporting facts, trigger.kind-specific instruction, "compose body + cta + rationale"

**Cache key:** `hash(category_id, category_version, merchant_id, merchant_version, trigger_id, trigger_version, customer_id, customer_version, language)`. Byte-identical output guaranteed on re-run.

## 7. Agent Architecture (ADR — rejected)

**Decision:** Sutra is deliberately non-agentic.

**Rejected alternatives:**
- Agentic planner-executor with tool use
- Multi-step reasoning chains
- Agent-style multi-turn composition within a single `/v1/tick` or `/v1/reply`

**Reasons:**
1. **Latency:** 30s/call cap punishes agent loops; serial composition of 20 actions = impossible.
2. **Determinism:** Agent decisions vary across runs even at temp=0.
3. **Cost:** Multi-call agent loops multiply LLM spend; risks $25 ceiling.
4. **Sufficient for task:** Composition is route→prompt→validate; no genuine multi-step reasoning required.
5. **Brief's own suggestion (§26):** "Build a prompt template… add a routing layer… add post-LLM validation" — single-step.

## 8. Data Flow (happy path sequence)

```
1. WARMUP
   harness → GET /v1/healthz (expect 0/0/0/0)
   harness → POST /v1/context × 255 (5 categories + 50 merchants + 200 customers)
   Sutra: stores each with version=1; marks fresh_context_pending=True
   harness → GET /v1/healthz (expect 5/50/200/0)
   warmup passes

2. PUSH TRIGGER
   harness → POST /v1/context (scope=trigger, version=1, payload={kind, urgency, ...})
   Sutra: stores; marks fresh; ack 200

3. TICK
   harness → POST /v1/tick {available_triggers: [...]}
   Sutra: 
     filter expired (trigger.expires_at < now)
     check suppression/topic/wait-state
     score & rank: urgency × freshness × merchant_priority
     pick top 3-5
     parallel composition (async):
       for each (merchant, trigger):
         check cache (hash) — if hit, return cached
         else: router → prompt assembly → facts registry → LLM call (25s timeout)
                → validation gate (13 checks) → cache write
         on LLM fail: secondary → templates
         on validation fail: re-prompt once → fallback template
     assemble actions[] (≤20)
     return
   harness: logs each action + rationale

4. REPLY
   harness: simulates merchant/customer reply (sometimes engaged, sometimes auto-reply, sometimes hostile)
   harness → POST /v1/reply {conversation_id, message, turn_number}
   Sutra:
     append turn to conversation_store
     classifier(message, conversation_history) → class
     state_machine(class, conversation_state) → action
     compose reply (send) OR wait (wait_seconds) OR end (rationale)
     return within 30s
   harness: continues to 5 turns or until bot ends

5. ADAPTIVE INJECTION (interleaved)
   harness → POST /v1/context (higher version for existing key)
   Sutra: atomic replace; mark fresh_context_pending=True
   next tick: composer detects fresh flag → leads with new-version fact
     validation gate: if pending and no new-version fact in output → reject

6. REPLAY (Phase 4, top-10 only)
   harness: standalone 5-turn replays for auto_reply_hell, intent_transition, hostile
   Sutra: classifier + state machine handles each per documented arc
```

## 10. Security Architecture

- **Secrets:** LLM API keys via environment variables; `.env` in `.gitignore`; never committed.
- **Payload containment:** Only LLM providers receive merchant/customer fields; nothing else.
- **Teardown:** `/v1/teardown` wipes all stores, registries, cache, logs (except anonymized spend aggregate).
- **No scraping:** No calls to magicpin/Google/GBP APIs.
- **Output scope:** All composed messages are for challenge evaluation only — not real merchant outreach.
- **Rate limit:** Single uvicorn worker; in-memory stores avoid race conditions; 10 req/s sustained via async handlers.

## 11. Failure Modes Matrix

| Failure | Detection | Automatic response | Point impact avoided |
|---|---|---|---|
| LLM call >25s | Hard timeout | Secondary provider; if also fails, fallback template | −1 tick timeout |
| LLM primary outage | HTTP 5xx / connection error | Secondary provider → templates | Zero-score tick |
| LLM secondary outage | HTTP 5xx / connection error | Templates only | Lower scores (5-7/dim) but no timeout |
| Validation gate reject (any check) | Check fails | Re-prompt once with stricter instruction; second fail → fallback template | Cap-5/dim or worse |
| Healthz count drift | Periodic self-check vs store | Re-derive counts; alert; manual fix if persistent | −10 + disqualification |
| Spend >$20 | Spend meter | Soft alert (Slack/log); continue | None (advisory) |
| Spend >$25 | Spend meter | Hard switch to fallback-only mode | Quota exhaustion mid-window |
| Host restart | Startup detects no state | Recover from disk snapshot (≤30s stale) | State loss; possible healthz fail if recovery slow |
| Stale version push | Version compare | 409 `stale_version` | Lost adaptation bonus (if accepted wrongly) |
| Verbatim repeat risk | Body-hash check pre-send | Skip action or re-compose | −2/repeat + cap-5/dim |
| URL in output | Validation check #1 | Reject; re-prompt; fallback template | −3/URL hard fail |
| Multiple CTAs | Validation check #3 | Reject; re-prompt; fallback template | Engagement penalty |
| Hallucination | Validation check #2 (facts membership) | Reject; re-prompt; fallback template | Cap-5/dim |
| Expired trigger | Pre-compose filter | Skip | No score, no penalty |
| Conversation in wait state | Pre-compose filter | Skip | No score, no penalty |
| Quota exhausted on primary | 429 from provider | Switch to secondary | Zero-score tick |

## 17. Technical Tradeoffs (ADR-01 … ADR-08)

### ADR-01: Hybrid composer over pure-LLM
**Decision:** Hybrid (LLM core inside deterministic guardrails).
**Rejected:** Pure-LLM (no validation gate).
**Reason:** Hallucination cap (5/dim), URL hard-fail (−3), multiple CTA penalty, latency risk (−1/timeout). Validation gate prevents all four. Fallback templates guarantee baseline score when LLM is down.

### ADR-02: Hybrid composer over pure-template
**Decision:** Hybrid.
**Rejected:** Pure-template.
**Reason:** Can't generalize to fresh injections (Phase 3). Can't earn Decision Quality 9-10 (no "added judgment"). Can't handle novel triggers unseen in 30 pairs. Brief warns: "Bots that pattern-match the simulator will fail."

### ADR-03: Hybrid composer over agentic planner-executor
**Decision:** Single-step pipeline.
**Rejected:** Agentic loops.
**Reason:** Latency (30s cap), determinism (agent variance), cost (multi-call), sufficient for task (route→prompt→validate).

### ADR-04: Cache by input hash for determinism
**Decision:** Hash-keyed response cache.
**Reason:** temp=0 is insufficient (sampling jitter, provider routing). Cache guarantees byte-identical output. Reduces cost ~3x.

### ADR-05: Top-K action selection per tick
**Decision:** Compose top 3-5 actions in parallel; skip rest.
**Reason:** Serial composition of 20 actions × 2-8s = 40-160s = timeout. Top-K by (urgency × freshness × priority) preserves best scores; restraint on rest.

### ADR-06: In-memory stores + 30s disk snapshot (no DB)
**Decision:** In-memory + atomic disk snapshot.
**Rejected:** Real database (Postgres/SQLite-as-DB).
**Reason:** Test window is 60 min; in-memory is faster (sub-millisecond); disk snapshot suffices for restart recovery. DB adds latency + failure modes + complexity.

### ADR-07: Multi-provider LLM fallback (not just templates)
**Decision:** Primary frontier → secondary fast on different provider → templates.
**Reason:** Single-provider outage = zero LLM-composed messages = 5-7/dim instead of 8-10. Multi-provider survives single outage.

### ADR-08: Heuristic classifier over LLM classifier
**Decision:** Regex-first classifier; LLM only as tiebreaker.
**Reason:** Latency (regex <1ms; LLM 1-3s). Determinism (regex is byte-deterministic; LLM has variance). Sufficient for 7 classes with documented patterns.
