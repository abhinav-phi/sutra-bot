# Rules — Sutra

## 1. Determinism Rules

| ID | Rule | Enforcement |
|---|---|---|
| D-01 | LLM temperature MUST be 0 | `llm/client.py` hardcodes `temperature=0` |
| D-02 | LLM top_p MUST be 1 | `llm/client.py` hardcodes `top_p=1` |
| D-03 | No RNG in composition path | No `random` module calls in `composer/` |
| D-04 | Canonical ordering: sort facts, lists before passing to LLM | `facts_registry.py` enforces sort |
| D-05 | Cache-first: check cache before LLM call | `composer/cache.py` lookup before `llm/client.py` |
| D-06 | Cache key includes all four context versions | Hash function in `composer/cache.py` |
| D-07 | Byte-equality regression test must pass | `tests/test_determinism.py` asserts identical output on 10 re-runs |
| D-08 | No fallback path uses RNG | Fallback templates are deterministic |
| D-09 | Post-processing is deterministic (whitespace, punctuation) | `validation_gate.py` post-process step |

## 4. Contract Rules

| ID | Rule | Enforcement |
|---|---|---|
| C-01 | Pydantic-validate every outbound response | Pydantic schemas in `schemas/pydantic_models.py` |
| C-02 | ≤20 actions per tick | Tick orchestrator hard cap |
| C-03 | All required action fields present | Pydantic schema requires: conversation_id, merchant_id, customer_id (nullable), send_as, trigger_id, template_name, template_params, body, cta, suppression_key, rationale |
| C-04 | `customer_id` is `null` not omitted when merchant-facing | Pydantic schema: `customer_id: str \| None = None` |
| C-05 | `send_as` is `"vera"` for merchant-facing, `"merchant_on_behalf"` for customer-facing | Composer logic |
| C-06 | `/v1/context` idempotent on `(scope, context_id, version)` | Context store version compare |
| C-07 | Same version ⇒ 200 no-op | Context store |
| C-08 | Higher version ⇒ atomic replace | Context store |
| C-09 | Lower version ⇒ 409 `stale_version` | Context store |
| C-10 | Malformed ⇒ 400 | Pydantic validation |
| C-11 | Payload >500 KB ⇒ 400 `payload_too_large` | Content-Length check |
| C-12 | Reply response: `action` in {send, wait, end} | Pydantic schema |
| C-13 | If `action=wait`, `wait_seconds` present and ∈ {900, 1800, 3600} | Pydantic validator |
| C-14 | If `action=end`, `rationale` present | Pydantic validator |
| C-15 | After `end`, no further messages on that conversation_id | Conversation store: `ended=True` immutable |

## 5. Latency Budget Rules

| ID | Rule | Enforcement |
|---|---|---|
| L-01 | LLM call ≤25s hard timeout | `llm/client.py` timeout=25 |
| L-02 | Reply classifier ≤10s (regex-first; LLM tiebreaker rare) | `reply/classifier.py` regex before LLM |
| L-03 | Tick total ≤28s hard (safety margin under 30s) | Top-K selection (3-5 parallel); cache-first |
| L-04 | `/v1/context` ≤100ms | In-memory store; no LLM work |
| L-05 | `/v1/healthz` ≤2s | Counts from store (O(n) but n small) |
| L-06 | Never block `/v1/context` on LLM work | Context endpoint doesn't call LLM |
| L-07 | Parallel composition for top-K actions | `asyncio.gather` in tick orchestrator |
| L-08 | Cache hit returns <100ms | `response_cache` dict lookup |
| L-09 | Disk snapshot write <500ms (atomic temp+rename) | `stores/snapshot.py` |
| L-10 | Warmup 255 context pushes complete <5s | Async handlers; in-memory store |

## 8. Cost Rules

| ID | Rule | Enforcement |
|---|---|---|
| K-01 | Spend meter on every LLM call | `llm/ledger.py` logs cost |
| K-02 | $20 soft alert (log + optional Slack) | `llm/ledger.py` threshold check |
| K-03 | $25 hard fallback-only switch | `llm/client.py` checks spend before call; if >$25, skip to templates |
| K-04 | Cache aggressively (cache-first) | `composer/cache.py` |
| K-05 | Top-K selection (3-5 per tick, not 20) | Tick orchestrator |
| K-06 | Regex-first classifier (avoid LLM for common case) | `reply/classifier.py` |
| K-07 | Fallback templates use 0 LLM tokens | `composer/fallback_templates.py` |
| K-08 | Estimated total spend: ~$7-10 | Within $25 ceiling |
| K-09 | Quota exhaustion handled (429 from provider) | `llm/client.py` catch; switch to secondary |
| K-10 | Spend aggregate preserved after teardown (billing audit) | `llm/ledger.py` aggregate only |

**Measured provider constraint (2026-09-01, [`9. ModelBench.md`](9.%20ModelBench.md) §5):** the api.b.ai endpoint enforces a **~9–10 req/min per-key rolling limit** — beyond that, `429` (K-09 path). Consequences: bench/simulator scripts pace calls ≥6.5s apart with backoff; the composer's top-K parallelism relies on the cache (K-04) rather than N live provider calls; and all six models are reasoning models, so `max_tokens ≥ 2000` (empty `content` + `finish_reason=length` = K-09-style provider failure → secondary → templates).

## 12. DO-NOT List

| ID | Don't | Reason |
|---|---|---|
| N-01 | No RAG / vector embeddings over dataset | Dataset small; direct lookup faster, deterministic, free |
| N-02 | No agent loops (planner-executor) | Latency risk; determinism; cost; overkill |
| N-03 | No serverless hosting | Cold starts + state loss violate 60-min persistence |
| N-04 | No database server (Postgres/MySQL) | In-memory + disk snapshot suffices; DB adds latency + failure modes |
| N-05 | No web UI / dashboard | Judge never sees it; README + bot URL only |
| N-06 | No multi-LLM ensemble voting | Adds latency + cost + nondeterminism |
| N-07 | No scraping real magicpin/Google data | Explicitly forbidden (§23) |
| N-08 | No per-merchant voice tuning beyond vertical | Per-vertical is enough; per-merchant is over-engineering |
| N-09 | No cadence RL / RL-based optimization | Heuristic restraint suffices |
| N-10 | No custom judge LLM | Use official `judge_simulator.py` |
| N-11 | No fine-tuning models | Not enough data; overfits to visible 30 pairs |
| N-12 | No A/B testing in production | Determinism requires single variant |
| N-13 | No external webhooks | Bot is polled via `/v1/tick`; no push needed |
| N-14 | No multi-tenant tables | One bot per submission |
| N-15 | No custom template_name system beyond `vera_{kind}_v1` | Meta won't actually be called; minimal suffices |
